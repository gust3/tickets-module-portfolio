# Отчёт о багах, исправлениях и принятых решениях

---

## 1. Состояние гонки (Race Condition) при переключении и сохранении

**Воспроизведение:** DevTools → Slow 3G → быстрый клик по списку заявок или двойной клик по кнопке «Сохранить». Данные на экране «прыгали», либо старое сохранение затирало новое.

**Причина:** Отсутствие отмены устаревших HTTP-запросов и отсутствие трекинга активных операций на клиенте. React слепо применял `setTicket` и `setHistory` при получении любого ответа, даже если пользователь уже переключился на другую заявку или инициировал новое сохранение.

**Исправление:**
- **Для загрузки:** добавлен `AbortController` и флаг `active` в `useEffect`.
- **Для сохранения:** введён массив `savingTicketIds`, хранящий ID заявок, для которых сейчас выполняется запрос. Кнопка блокируется, если ID текущей заявки есть в массиве. Это предотвращает повторную отправку даже после ухода с заявки и возврата.
- **Защита от позднего ответа:** локальный UI (`setTicket`, `setHistory`, `setMessage`) обновляется только если `savedTicketId === selectedId`.

**Проверка:** Ручное тестирование в браузере с троттлингом сети (Slow 3G). UI не перезаписывается устаревшими данными.

---

## 2. Список заявок не обновляется после сохранения в фоне

**Воспроизведение:** Сохранить заявку → сразу переключиться на другую → дождаться ответа. Список слева оставался со старым источником.

**Причина:** Вызов `onChanged(data.ticket)` стоял после проверки `if (savedTicketId !== selectedId) return;`. Если пользователь уже переключился, уведомление родителю не уходило, и список не обновлялся.

**Исправление:** Вызов `onChanged(data.ticket)` перенесён **до** проверки актуальности заявки. Таким образом, родительский компонент (`App.jsx`) всегда получает актуальные данные для обновления списка, а локальный UI карточки обновляется только при совпадении ID.

**Проверка:** Ручное тестирование: сохранить заявку, сразу переключиться на другую — источник в списке обновляется мгновенно.

---

## 3. Падение карточки при отсутствии источника (Баг №2)

**Воспроизведение:** Запрос `GET /api/tickets/{id}` для заявки с `source_id = NULL`.

**Причина:** SQL-запрос `SELECT ... WHERE id=NULL` возвращает пустой результат. `pg_fetch_assoc()` возвращает `false`, и попытка обратиться к `$source['id']` вызывает PHP Warning, который глобальный обработчик превращает в HTTP 500.

**Исправление:** В `TicketRepository::find()` добавлена явная проверка `if ($row['source_id'] !== null)` перед вторым запросом. Если источника нет, возвращается `'source' => null`.

**Проверка:** Автоматический регрессионный тест `test_null_source` (создаёт заявку, проверяет ответ, удаляет заявку).

---

## 4. Отсутствие серверных проверок прав и порядка валидации (Баг №3)

**Воспроизведение:** Отправка POST-запроса от имени роли `viewer` или для архивной заявки.

**Причина:** Проверка прав `FUNC_TICKETS_SOURCE_EDIT` и статуса архива существовала только во фронтенде. Порядок валидации в бэкенде нарушал ТЗ (источник проверялся раньше архива).

**Исправление:**
- В `routes.php` добавлен `requirePermission`.
- В `TicketRepository::changeSource()` выстроен строгий порядок:
    1. Наличие заявки (404)
    2. Запрет архива (403)
    3. Корректность источника (400)

**Проверка:** Тесты `test_permissions_viewer` и `test_validation_order`.

---

## 5. Атомарность и избыточные записи в истории

**Воспроизведение:** Теоретический сбой БД между `UPDATE` и `INSERT`, либо выбор того же источника.

**Причина:** Запросы выполнялись без транзакции. При повторном выборе того же источника создавалась мусорная запись в истории.

**Исправление:** Оба запроса обёрнуты в `BEGIN` / `COMMIT` / `ROLLBACK`. Добавлена ранняя проверка: если `source_id` не изменился, транзакция не начинается.

**Проверка:** Тест `test_successful_change_consistency` проверяет согласованность карточки, списка и истории.

---

## 6. Потеря сессии не обрабатывается на клиенте

**Воспроизведение:** Удалить cookie сессии в DevTools → кликнуть по заявке. Приложение показывало старые данные из стейта, в консоли сыпались ошибки 401.

**Причина:** Ни один компонент не обрабатывал HTTP 401 централизованно.

**Исправление:** В `api.js` добавлен глобальный колбэк `onSessionExpired`. При получении 401 от любого запроса React сбрасывает стейт (`employee`, `tickets`, `sources`, `selectedId`) в `App.jsx`, мгновенно возвращая пользователя к форме логина без перезагрузки страницы.

**Проверка:** Ручное удаление cookie сессии → клик по заявке → мгновенный возврат к форме логина.

---

# Решения и компромиссы

### Управление стейтом в React
Для блокировки кнопки сохранения использован массив `savingTicketIds` через `useState`, а не `useRef`, так как UI должен реагировать на изменение состояния блокировки. Массив выбран вместо одного ID, чтобы корректно обрабатывать сценарий, когда пользователь сохраняет несколько заявок параллельно — каждая разблокируется независимо в своём `finally`.

### Запросы на сохранение не отменяются через AbortController
Это осознанный выбор: POST-запрос, уже ушедший на сервер, должен быть выполнен до конца, чтобы не было рассинхрона между клиентом и БД. Защита от дублирования реализована на уровне UI (массив `savingTicketIds`), а не на уровне сети.

### Архитектура обработки ошибок
В production-проектах для глобальной обработки 401 обычно используют interceptors (axios) в связке со стейт-менеджером (Redux/Zustand). В рамках данного задания выбран более лёгкий подход — колбэк-подписка в кастомной обёртке над `fetch`. Это позволило избежать дополнительных зависимостей и сохранить прозрачность кода, при этом полностью решив задачу централизованной обработки потери сессии.

### Тестирование
Выбран подход **behavior-based integration tests** (проверка HTTP-ответов и целостности данных), а не unit-тесты или сканирование кода.

### Компромисс по тестированию транзакций
Полноценное тестирование отката (`ROLLBACK`) при сбое посередине транзакции требует механизмов fault injection (имитации сбоев), что выходит за рамки простого PHP-скрипта без тяжёлых фреймворков. Тесты подтверждают консистентность успешного исхода (буква **C** в ACID), что является стандартной прагматичной практикой.

## Одновременное редактирование

Если два сотрудника одновременно попытаются изменить источник одной и той же заявки:

- **На уровне БД:** PostgreSQL (в режиме изоляции `Read Committed` по умолчанию) гарантирует, что `UPDATE` выполнится атомарно. Вторая транзакция либо дождётся завершения первой, либо (при использовании `SELECT ... FOR UPDATE`) получит блокировку. Рассинхрона между `tickets` и `ticket_history` не произойдёт благодаря транзакциям.
- **На уровне истории:** в `ticket_history` будут записаны обе операции последовательно с корректными `old_source_id` и `new_source_id`.
- **На уровне UI:** если сотрудники не обновят страницу, они будут видеть устаревшие данные. Для предотвращения этого в production-системах обычно добавляют опрос (polling) или WebSocket-уведомления, а также блокировку карточки на уровне БД (`FOR UPDATE`).

## Оставшиеся ограничения

- **Исходный коммит:** по требованию ТЗ должен был быть отдельный коммит с исходным кодом до исправлений. В процессе работы коммиты делались инкрементально по мере обнаружения проблем, поэтому отдельный «initial» коммит не был создан. История Git отражает последовательность инженерного анализа.
- **E2E тесты фронтенда:** автоматические тесты покрывают только бэкенд. Проверка React-специфичных гонок (Race Condition) оставлена в формате ручных сценариев, так как настройка Playwright/Cypress в рамках данного тестового задания была бы избыточной.
- **Обновление списка заявок:** обновление списка после сохранения делегировано родительскому компоненту (`App.jsx`) через пропс `onChanged`. Если родительский компонент не реализует обновление своего стейта при получении этого колбэка, список не обновится автоматически без перезагрузки страницы.
